# LLP 0010.002: Ship: Tasks Done End to End

**Type:** Spec
**Status:** Active
**Systems:** LLP, Agents
**Author:** Charlie Cheever / Claude
**Date:** 2026-08-23
**Related:** LLP 0010, LLP 0005, LLP 0004

## Summary

The normative contract for `llp-ship`: plan, execute in isolated run-namespaced lanes, verify and review the exact integrated SHA, deliver per repo policy, clean up without destroying recoverable work. Extracted verbatim from [LLP 0010 §3](./0010-skill-install-super-refine-ship.rfc.md#3-llp-ship) (rationale and acceptance tests stay there). **MUST / "never" / bolded gates are contract; *(advisory)* is recipe** (LLP 0004).

## Trigger and preflight

A human hands over task references — Linear tickets, filesystem tickets, LLP documents, or free text — via `/llp-ship <ref...> [--base <branch>] [--mode local|pr|direct]`. Preflight discovers and states, before any mutation: the git repo and base branch (git is **required**; in a non-git project the skill refuses and offers plain task execution outside this contract); the recorded base SHA and its upstream relationship (pre-existing unpushed commits are surfaced and never made remotely reachable by this run without explicit consent); the verification commands available (the project's tests; `ref-check` where present — optional per LLP 0001, absence stated, not papered over); reviewer availability, when the review intensity in effect requires one (no reviewer at `same-family`+ → `blocked`; at `none`, none is needed); and the delivery mode and review intensity. **Authority:** the policy file's recorded mode is a *default and ceiling*, read from the recorded base commit — it is not itself authorization. External writes (`pr`, `direct`) are authorized by the human invocation that requested them, with the mode stated at preflight; task *content* never grants or escalates authority. Runs are single-flight per repo (an unreconciled run ledger blocks a new run until recovered). Any missing mandatory capability stops the run as `blocked`, honestly.

## Task gating

A proposal-shaped LLP task — one whose design others will implement, regardless of its `Type:` — must be `Accepted` before a delivering run implements it (LLP 0005). If it isn't, ship stops: the author can accept it (their action, not ship's) and re-invoke, or direct an explicitly-labeled **experiment run**, which implements on run branches and delivers nothing. Ship never applies *author-authority* transitions (`Accepted`, tombstoning). `Accepted` → `Active` is different — LLP 0005 defines it as the factual completion transition, and it is **not author-restricted**: anyone completing and delivering the implementation may apply it. When a delivered candidate completely implements an `Accepted` document, the flip is included in the gated candidate as a clearly-called-out commit, named in the run report/PR body so the delivering human is knowingly endorsing it. A partial implementation states its partial state and flips nothing. (LLP 0005 gains a clarifying clause to this effect with Phase 3.)

## Plan phase

Read every task fully (each task's source and content hash snapshotted in the run ledger); orient via governing docs; restate free-text tasks as a concrete plan before executing. Build the dependency graph and choose lanes *(advisory: independent tasks parallel in separate worktrees; dependent tasks sequenced in one lane)*. If lanes will create LLP documents, reserve their numbers serially at plan time — no `max + 1` race at merge within this invocation (cross-invocation collisions follow LLP 0000 §Numbering's renumber-on-integration rule, which closed LLP 0009 OQ1). Before creating anything, write the **run ledger** (durable, local, prunable after reconciliation; e.g. `.llp/ship-runs/<run-id>.json`): run id, base SHA, mode, task snapshots, and every branch/worktree the run creates — written before creation, updated at each gate. Git refs remain the source of truth; the ledger records intent and evidence, and a later invocation reconciles it against git to find and offer to reclaim orphans.

## Execute, integrate, gate

The base branch is immutable during execution — every run, including single-task runs, works on run-namespaced branches (`llp-ship/<run-id>/…`) and integrates on a run-specific integration branch cut from the recorded base SHA. Per lane: implement with commits at natural boundaries, co-evolving docs and `@ref`s (LLP 0004); run lane-local verification for fast feedback. Then the gates, indexed by commit SHA:

- **CANDIDATE(SHA):** all lanes merged into the integration branch, conflicts resolved.
- **VERIFIED(SHA):** the stated verification suite passes on a clean checkout of exactly this SHA (a run that mutates tracked files fails the gate — the mutation belongs in a commit).
- **REVIEWED(SHA):** review intensity is **tunable policy, not invariant** (capability-graded per LLP 0004 — the right default falls as models improve): repo policy or invocation selects `none` | `same-family` (default) | `cross-family` (§2's primitive). When any review runs: a fresh, independent session that wrote none of the code reviews the integrated diff and issues an **explicit verdict that no material finding remains** for this SHA — a review having occurred is not the gate; the verdict is. The reviewer never implements its own findings: material findings go to an implementing session, producing a new SHA that re-enters at CANDIDATE. Findings, dispositions, verdict, and the intensity in effect are recorded in the run report; at `none`, the report states plainly that delivery was unreviewed. What stays invariant at every intensity is honesty: claimed review must be real, SHA-bound, and independent.
- **DELIVERED:** only a SHA currently holding VERIFIED (and REVIEWED, at any intensity above `none`) may deliver, and delivery re-resolves local and remote base refs first — if either moved from the recorded SHA, reintegrate and re-gate or end `blocked`. Base advances only by fast-forward with an expected-old-SHA check; the outbound commit closure is computed before any push, and every commit that would become remotely reachable must be run-owned or explicitly authorized.

## Delivery modes

With no recorded policy **the default is `direct`** — shipping means shipping: the human invoking ship is choosing to push, and that invocation is the authorization (author decision, 2026-07-23). Repos that want a PR gate record `pr` (or `local`) in policy — the delivery-flag install asks exactly this question, so consuming repos set their own default at install time and the naked default chiefly governs the solo-maintainer case. **`local`**: fast-forward the local base; push nothing. **`pr`**: push the integration branch and open a pull request; base untouched. **`direct`**: advance and push the base; before pushing, state exactly which commits will publish; a rejected push (branch protection, divergence) falls back to `pr` behavior, reported factually. Ship's external effects are limited to git delivery (pushes, PR creation) — a task implying other external effects (deploys, package publishes, tracker writes) is out of ship's scope, and that portion is reported as out-of-scope rather than silently attempted. External steps can partially succeed; the ledger records **each external effect as its own fact** (e.g. `branch-pushed`, `pr-opened`, `remote-base-advanced`), the run reconciles those facts against the remote before any retry, and a task's terminal status always enumerates them — a task may end `blocked` on a remaining step (say, PR creation), but a report MUST NOT conceal or contradict an effect that succeeded (the branch *is* pushed, and the report says so). PR creation is a capability-checked attempt; work is preserved, never force-pushed. Multi-task delivery is atomic by default: one gated SHA delivers everything; delivering a reduced subset requires renewed human approval and full re-gating. The run report (task outcomes, verification output, review verdict and dispositions, delivered SHA) goes in the PR body in `pr` mode and is retained in the run ledger in `local`/`direct` modes.

## Invariants

- MUST NOT report verification or review that did not run; failed checks are reported as failures. Both gates MUST hold for the exact SHA delivered.
- MUST NOT count a self-review as the review: at any intensity above `none`, the reviewer is distinct from every implementing session and never implements its own findings; at `none`, the report MUST say the delivery was unreviewed.
- MUST NOT force-push, and MUST NOT make any commit remotely reachable that the run did not create, absent explicit consent.
- MUST record every created branch/worktree in the run ledger before creating it, namespace them `llp-ship/<run-id>/`, and clean up only state that is clean and durably integrated. MUST NOT delete a dirty worktree or a branch holding unique unmerged commits — on failure or abort, preserve them and report exact recovery instructions.
- MUST leave unrelated local changes and commits untouched; uncommitted user changes that block the plan → stop and ask, never stash silently.
- MUST report per task: done (with commits), blocked (on what), or failed (with actual output) — and after any external effect, the factual outcome of that effect.
