**Type:** Spec

## Summary

The normative contract for how LLP skills reach a consuming repository and stay current: releases are git tags, installations carry receipts, updates are three-way-checked, diff-approved, and recoverable. Extracted verbatim from [LLP 0010 §1](./0010-skill-install-super-refine-ship.rfc.md#1-installation-and-updates-llp-adopt-extended) (the rationale and rejected alternatives stay there) so that the binding policy lives in a foundation document rather than only in an RFC plus `SKILL.md` MUSTs (LLP 0009). Implemented by `llp-adopt`. Throughout: **anything phrased as MUST, "never", or "Contract:" is contract; mechanics marked *(advisory)* are recipe** (LLP 0004).

## Releases and receipts (the trust model)

The `source:` frontmatter pin stays informational (LLP 0008/0009). A **release is a git tag** of this repo — git's own content addressing makes the tag's tree the exact, verifiable release contents; no separate manifest file is needed, and none is added. Two disciplines replace it:

- **Release discipline:** a commit that changes a skill file is not installable until a new tag is published. (This is what the `llp-maintain`-after-`v0.2.0` example violated.)
- **Install receipts:** installing writes a receipt *next to the installation it describes* — a repo-scoped install puts it in that repo (e.g. `.llp/skills-receipt.json`, committed, as is the policy file below; ship's run records are local and prunable); a user-global install (some runtimes are user-global per LLP 0008's table, which is advisory and confirmed against the runtime's current documentation at install time) puts it in that user-global location, and one receipt never claims to describe more than its own installation. The receipt records: origin URL, tag, the tag's resolved commit, the installed profile flags, and a content hash per installed file, computed from the fetched tree at install time. The receipt — written by an explicit, human-approved run — is the trust root for later updates; fork detection is a local hash comparison and needs no network.
- **Threat model (stated):** this covers accidental drift, stale copies, and transport corruption. A compromised upstream account or force-moved tag is out of scope — the same trust extended to any git dependency — with signed-tag verification noted as future hardening. A moved tag is *detected* (re-resolution no longer matches the receipt's commit) and stops the run. The receipt itself is editable state: a hand-edited receipt defeats fork detection, which stays inside the accidental-drift scope — the receipt attests, it does not prove.

## Install

After writing the managed blocks, `llp-adopt` offers to install skills into the consuming repo's runtime skill directory. The install unit is a profile — **core** (default: the five existing skills, unchanged from LLP 0008; `llp-adopt` installs itself, and its update mode keeps the installation current) plus two **additive opt-in flags**: **review-plus** (`llp-super-refine`) and **delivery** (`llp-ship`, which also asks one question — this repo's default delivery mode, `local`, `pr`, or `direct` (§3) — recorded in a committed repo-local policy file, e.g. `.llp/policy.json`, never in a user-global receipt). Profile membership is defined by this RFC and, per release, by the tag's adopt contract. Installation is a copy, never a symlink. Existing security rules apply: confirm before writing, project-local may proceed more freely than user/global directories, reruns are idempotent, a file whose hash doesn't match the receipt is never overwritten without showing a diff, and user-global installs warn that they affect every repo for that user and require explicit confirmation.

## Update (a mode of `llp-adopt`)

Invoked as `/llp-adopt update` — and "update the LLP skills" routes here. An earlier revision made this a separate `llp-update-skills` skill; review showed the separation argument didn't hold: adopt already performs verified, diff-shown, receipt-writing update work in its bootstrap and migration paths, and a separate skill would duplicate that surface while growing the always-loaded core (LLP 0008, "Modes instead of more skills"). The posture boundary that matters — llp-maintain *never applies*, adopt applies after an approved diff — is preserved: llp-maintain's audit keeps its stale-pin note and hands off here.

1. Read the receipt for this installation (none → offer a fresh install, which bootstraps one; pre-receipt consumers migrate the same way). Runs are **single-flight** per installation: an unfinished update journal or unreconciled run state blocks a new run until recovered.
2. Resolve upstream: list release tags, resolve the chosen (default: newest) tag to its commit, fetch that tree *(advisory: shallow clone or tag archive; git is a prerequisite for install/update)*.
3. **Three-way check** per file: installed copy vs. receipt hash. Any mismatch means the project forked a managed file — the coupled update **aborts** (skills reference each other; mixed-release installs are not a supported state). The run reports the fork and offers resolution paths; it never clobbers, and it reruns only after resolution. Resolution is binary per file: discard the fork (restoring a managed copy), or **detach** it — the file leaves the managed set permanently, the receipt records the detachment, and the remaining managed files stay a complete coupled set for the profile *minus its detached members*, which later updates treat as user-owned (upstream changes to a detached file are noted, never applied). Detachment is not a supported-mixed release; it is a smaller managed set beside user-owned files.
4. Compute the changeset for the installed profile *as defined at the target tag* (adds, removals, renames included), present the full diff as one set, and on approval apply it. **Contract:** the state approved is revalidated immediately before mutation (a file edited between approval and apply aborts); an interrupted update is recoverable to either endpoint; the receipt write is the commit point; prior bytes remain retrievable until the update completes. *(Advisory mechanics: stage outside the target, journal the run, back up prior bytes, move, write receipt last; rollback after completion is `git revert` where the installation is committed, the backups otherwise.)*
5. If upstream is unreachable, a tag has moved or vanished, or fetched content can't be verified against the resolved commit: report exactly that and **write nothing**. Cannot-verify never degrades to guess.

**Staleness nudges *(advisory)*.** Detection is decoupled from application: `llp-maintain --intent audit` notes a stale pin, and `llp-orient` may surface the same one-line nudge at orientation time (receipt tag vs. `git ls-remote --tags`, skipped offline). A nudge only ever points at `/llp-adopt update` — nothing updates implicitly.

## Release discipline (this repository)

A commit that changes a skill file is not installable until a new tag is published. Release checklist *(advisory)*: bump `source:` pins and pinned URLs → commit → tag → push tag. Release validation, if ever automated, is a separate composable check — `ref-check` keeps its single purpose (LLP 0009).
