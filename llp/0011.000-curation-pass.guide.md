# LLP 0011.000: The Curation Pass

**Type:** Guide
**Status:** Active
**Systems:** LLP
**Author:** Charlie Cheever / Claude
**Date:** 2026-08-22
**Related:** LLP 0011, LLP 0000, LLP 0004

## Summary

How to run the periodic pass that keeps `llp/foundation/` a true kernel, `llp/current/` an honest picture of what's in play, and the code in line with foundation. Three verbs, always in this order: **promote → archive → realign**. `llp-maintain --intent curate` runs it; this document is the procedure it follows. It proposes; a human applies.

The rules it enforces are normative and live in [LLP 0000 §1](./0000-linked-literate-programming.explainer.md#current-and-foundation); the rationale is [LLP 0011](./0011-llp-v2-overlays-and-sub-llps.rfc.md). Everything below the rules is recipe.

## When

- After a stretch of design work lands (an RFC accepted, a spec finalized).
- Before a release.
- On a cadence when neither has happened — monthly is a fine default for an active project.
- Whenever `ls llp/current` makes you wince.

## Promote

Goal: foundation is the smallest set of documents from which the project could be recreated.

1. List candidates: every `Active` document not in `foundation/`, plus every `Accepted` RFC whose implementation has landed.
2. For each, apply the admission test — *would deleting this, with the rest of foundation and the code intact, lose something unrecoverable?* Explainers, principles, and current-truth specs usually pass. RFCs usually fail even when accepted: they are proposal plus history. What survived from them belongs folded into a living document.
3. Fold before linking. If an accepted RFC's decisions aren't yet stated in a foundation document, edit that document (or create the spec as a sub-LLP of the RFC, e.g. `NNNN.000-…spec.md`), then link the living document. Mark the RFC `Superseded` or leave it `Active` as a rationale record — but don't link it.
4. Re-test existing members. Anything that no longer passes is unlinked; foundation should shrink as often as it grows.
5. Foundation entries must be `Active`; `ref-check` refuses anything else.

> **Recipe (advisory)** — `ls llp/foundation` should read like a table of contents for a newcomer. If two entries overlap, that's a merge waiting to happen; if an entry needs another non-foundation document to make sense, either promote that one or fold it in.

## Archive

Goal: `current/` contains exactly what someone is thinking about.

1. For each link in `current/`, ask: has this been edited, reviewed, or cited in a conversation recently? If not, `rm` the link. The document is untouched.
2. Newly created documents land in `current/` by default (`llp-create` does this). A document that was created and never worked on again is the commonest stale entry.
3. While you're there, fix statuses: a `Draft` nobody has touched in months is a candidate to tombstone or to finish; a `Review` with its loop concluded should be `Accepted` or `Draft`; a document whose claims turned out wrong becomes `Tombstoned` (with `**Superseded by:**` if something replaced it). Tombstoned and Superseded documents can't be in either overlay — unlink them.

> **Recipe (advisory)** — a staleness heuristic: `git log -1 --format=%cs -- llp/NNNN-*` older than ~30 days and not referenced in any open PR or branch → propose unlinking. Treat it as a prompt, not a rule.

## Realign

Goal: the code does what foundation says.

This is the step with teeth, and the inverse of `llp-maintain`'s usual drift check. Drift asks "the code changed — does the doc still describe it?" Realign asks "the doc is the truth — does the code comply?"

1. For each foundation document, walk its normative sections (contract, not recipe — see LLP 0000 [Contracts and recipes](./0000-linked-literate-programming.explainer.md#contracts-and-recipes)).
2. For each normative claim, find the code that should implement it: follow inbound `@ref`s (`grep -rn 'LLP NNNN' --exclude-dir=llp`), then look for the unreferenced places it should govern.
3. Classify: **compliant** (note where, propose a `@ref` if missing) · **diverged** (propose the code change, or — if the code is right and the doc is wrong — propose the doc change and say which) · **unimplemented** (propose a task; hand to `llp-ship` if the repo uses it).
4. Don't realign against anything outside foundation. A non-foundation `Active` spec is still binding for the code it covers, but it's `pre-pr`/`audit` drift-check territory; the curation pass keeps its attention on the kernel.

## Output

One checklist, grouped under the three headings, each line an action with a one-line reason:

```
PROMOTE
  + link 0012-auth-model.spec.md            foundational: only statement of the session-token contract
  ~ fold 0009 §decisions into 0000 §6       accepted RFC; kernel should state it, RFC stays as rationale
  - unlink 0005                              process guide; recreatable from 0000 + the skills
ARCHIVE
  - unlink 0011.000 from current             finished; no edits since acceptance
  ! 0007 Draft → Tombstoned                  superseded by 0012; add Superseded-by
REALIGN
  * ref-check: overlay rules (0000#current-and-foundation) → compliant, ref present
  * llp-create: link into current/ (0000#current-and-foundation) → diverged; propose skill edit
```

Nothing is applied until a human says so. Apply in the order shown — promotions and tombstones can change what realign should check.

## Anti-patterns

- **Foundation as a trophy case.** "Important" is not the test; "unrecreatable without" is.
- **Current as a to-do list.** Current is what's being thought about, not what should be. Use issues for the latter.
- **Archiving by moving files.** Never. Links come and go; documents stay put.
- **Realigning against a stale foundation.** Promote first, so realign has the right truth to compare against.
