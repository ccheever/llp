## Summary

How to run the periodic pass that keeps `llp/foundation/` a true kernel, `llp/current/` an honest statement of what's in play, and the code in line with foundation. `llp-maintain --intent curate` runs it; this document is the procedure it follows.

The **contract** is in LLP 0000 [Current and foundation](./0000-linked-literate-programming.explainer.md#current-and-foundation): verbs in the order promote → archive → realign; propose, never apply; realign against `foundation/` only, after checking each foundation claim against every other binding `Active` document and resolving conflicts in the same pass; the admission test. The rationale is [LLP 0011](./0011-llp-v2-overlays-and-sub-llps.rfc.md). Everything in this guide that is not a restatement of that contract — cadence, heuristics, checklist format, worked examples — is recipe.

## When

> **Recipe (advisory)** — after design work lands (an RFC accepted, a spec finalized); before a release; monthly otherwise; whenever `ls llp/current` makes you wince.

## Promote

Goal: foundation is the smallest set of documents from which the project could be recreated.

1. List candidates: every `Active` document not in `foundation/`, plus every `Accepted` RFC whose implementation has landed.
2. For each, apply the admission test (LLP 0000): *could the design — decisions in force, constraints on code, the rationale that keeps decisions from being re-made — be recreated from the proposed foundation set without this document?* Design, not a runnable tree; not history. Explainers, principles, and current-truth specs usually pass. RFCs usually fail even when accepted: proposal plus history, with the survivors folded into a living document. A guide passes when its procedure is itself a design commitment.
3. Fold before linking. If an accepted RFC's decisions aren't yet stated in a foundation document, edit that document (or create the spec as a sub-LLP of the RFC, e.g. `NNNN.000-…spec.md`), then link the living document. Mark the RFC `Superseded` or leave it `Active` as a rationale record — but don't link it.
4. Test the set, not the members. Build the proposed foundation set first; then test removals one at a time against *that* set, re-testing after each removal. Never test two overlapping documents pairwise — each looks removable while the other is present. The set is done when it is collectively sufficient and no single member is removable.
5. Check for too small. Orient from `ls llp/foundation` alone, as a newcomer would: if a constraint that binds code today isn't reachable from there, foundation is missing something — promote it or fold it in. Too small fails the same way too large does.
6. Foundation entries must be `Active`; `ref-check` refuses anything else.

> **Recipe (advisory)** — worked on this corpus: 0000 passes (root; grammar and lifecycle live nowhere else); 0004 passes (principles that decide future disputes); 0005 passes on its honesty rules, fails on its recipe — fold the rules into 0000 or promote it whole, not half; 0009 fails (accepted, survivors already in 0000/0004 — stays as rationale); 0003 fails (research).

## Archive

Goal: `current/` contains exactly what someone is thinking about.

1. For each link in `current/`, ask: is the work this entry declares still in progress — edits, review, implementation, discussion? If not, propose removing the link. The document is untouched. On a shared branch, removals for work someone else owns are proposals to them, not unilateral.
2. Newly created documents land in `current/` by default (`llp-create` does this). A document that was created and never worked on again is the commonest stale entry.
3. While you're there, fix statuses: a `Draft` nobody has touched in months is a candidate to tombstone or to finish; a `Review` with its loop concluded should be `Accepted` or `Draft`; a document whose claims turned out wrong becomes `Tombstoned` (with `**Superseded by:**` if something replaced it). Tombstoned and Superseded documents can't be in either overlay — unlink them.

> **Recipe (advisory)** — a staleness heuristic: `git log -1 --format=%cs -- "llp/<full dotted number>-"*` (e.g. `llp/0011.000-*`) older than ~30 days and not referenced in any open PR or branch → propose unlinking. Treat it as a prompt, not a rule.

## Realign

Goal: the code does what foundation says.

This is the step with teeth, and the inverse of `llp-maintain`'s usual drift check. Drift asks "the code changed — does the doc still describe it?" Realign asks "the doc is the truth — does the code comply?"

1. For each foundation document, walk its normative sections (contract, not recipe — see LLP 0000 [Contracts and recipes](./0000-linked-literate-programming.explainer.md#contracts-and-recipes)).
2. **Conflict check first.** For each normative claim, grep the other `Active` normative documents (specs, decisions, principles outside foundation) for the same subject. A contradiction is resolved in this pass before anything else: foundation wins and the other document is updated, folded, or marked `Superseded` — or the foundation claim is the wrong one, in which case fix foundation and go back to Promote. Never propose code against a known contradiction.
3. For each normative claim, find the code that should implement it: follow inbound `@ref`s (`grep -rn 'LLP NNNN' --exclude-dir=llp`), then look for the unreferenced places it should govern.
4. Classify: **compliant** (note where, propose a `@ref` if missing) · **diverged** (propose the code change, or — if the code is right and the doc is wrong — propose the doc change and say which) · **unimplemented** (propose a task; hand to `llp-ship` if the repo uses it).
5. Don't realign against anything outside foundation. A non-foundation `Active` spec is still binding for its code — step 2 keeps it from contradicting the kernel — but its own drift is `pre-pr`/`audit` territory.

## Output

> **Recipe (advisory)** — the format below is a convention, not a contract.

One checklist, grouped under the three headings, each line an action with a one-line reason:

```
PROMOTE   + link 0012-auth-model.spec.md      only statement of the session-token contract
          ~ fold 0009 §decisions into 0000    accepted RFC; kernel states it, RFC stays as rationale
ARCHIVE   - unlink 0011.000 from current      finished; no edits since acceptance
          ! 0007 Draft → Tombstoned           superseded by 0012; add Superseded-by
REALIGN   * llp-create vs 0000#current-and-foundation → diverged; propose skill edit
```

Nothing is applied until a human says so. Apply in the order shown — promotions and tombstones can change what realign should check.

## Anti-patterns

- **Foundation as a trophy case.** "Important" is not the test; "unrecreatable without" is.
- **Current as a to-do list.** Current is what's being thought about, not what should be. Use issues for the latter.
- **Archiving by moving files.** Never. Links come and go; documents stay put.
- **Realigning against a stale foundation.** Promote first, so realign has the right truth to compare against.
- **Code as tiebreaker.** If another `Active` spec disagrees with foundation, the pass resolves that first; code is never the arbiter.
