**Related:** LLP 0004, LLP 0005, LLP 0008, LLP 0009

## Summary

Three additions to the skills system, growing it from five skills to seven — two new skills plus a new mode of an existing one. This RFC is accepted or rejected **as one unit** (one document, one `Status:`, per LLP 0005); its implementation phases land independently, and if a part is later cut, that is recorded as a dated addendum or a superseding LLP, never inferred from prose.

1. **Close the distribution loop.** [LLP 0008](./0008-distributed-agent-skills.rfc.md#distribution) decided that skills reach consuming projects as pinned copies, and llp-maintain's contract already *notes* stale pins — but nothing installs the copies and nothing applies updates. `llp-adopt` gains an **install step** and an **update mode**, backed by tagged releases and per-installation receipts.
2. **`llp-super-refine`** — the author-authorized "refine until two independent model families both say ready" loop, proven on single documents in the `exact` project, specified here with auditable rounds, bounded budgets, and a multi-document design.
3. **`llp-ship`** — hand it one or more tasks and it plans, executes in isolated lanes, verifies and reviews the exact integrated commit, and delivers via the repo's chosen delivery mode.

All three inherit the standing rules: skills are ≤60-line contracts citing their governing policy (LLP 0009), review honesty is absolute (LLP 0005), and docs co-evolve with code (LLP 0004). Each part pins behavioral protocol — consent around writes, honesty around review, safety around delivery — which is what the capability test says survives model improvement. Throughout this document, **Invariants lists and anything phrased as MUST are contract; mechanics phrased as "e.g." or marked *(advisory)* are recipe** (LLP 0004, "Contracts over recipes"). Contract clauses state outcomes; how an implementation achieves them is phase work unless a MUST says otherwise.

## Motivation

**Distribution is half-built.** Today a consuming project gets LLP skills by someone hand-copying directories. Staleness *detection* is already specified — llp-maintain's audit notes a `source:` pin that lags upstream — but nothing installs the copies, nothing verifies what an installed copy corresponds to, and nothing applies an update. Without the full loop, every consuming repo silently forks the skills the day they're copied. (The authoring repo itself demonstrates the verification gap: `skills/llp-maintain/SKILL.md` was edited after the `v0.2.0` tag it pins, so a copy of HEAD would immediately diverge from its declared pin.)

**Super-refine earned promotion.** The dual-model refine-until-ready loop has run repeatedly in `exact` and produces materially better documents than single-pass review — this claim is experiential, not yet measured; the loop's artifacts under `llp/reviews/` are the evidence trail a future Research LLP can mine. Related LLPs are usually drafted together; the multi-document generalization is the part that needs design, so it belongs in the first-party corpus.

**Ship pins down a recurring improvisation.** "Take these tickets and do them end to end" is already a common request; each time, the agent re-improvises worktree strategy, verification depth, and cleanup. The failure modes — fabricated verification, self-review rubber-stamping, orphaned worktrees, unauthorized publication — are exactly the kind of invariants LLP 0008 says skills exist to pin.

## Design

### 1. Installation and updates (`llp-adopt`, extended)

**Releases and receipts (the trust model).** The `source:` frontmatter pin stays informational (LLP 0008/0009). A **release is a git tag** of this repo — git's own content addressing makes the tag's tree the exact, verifiable release contents; no separate manifest file is needed, and none is added. Two disciplines replace it:

- **Release discipline:** a commit that changes a skill file is not installable until a new tag is published. (This is what the `llp-maintain`-after-`v0.2.0` example violated.)
- **Install receipts:** installing writes a receipt *next to the installation it describes* — a repo-scoped install puts it in that repo (e.g. `.llp/skills-receipt.json`, committed, as is the policy file below; ship's run records are local and prunable); a user-global install (some runtimes are user-global per LLP 0008's table, which is advisory and confirmed against the runtime's current documentation at install time) puts it in that user-global location, and one receipt never claims to describe more than its own installation. The receipt records: origin URL, tag, the tag's resolved commit, the installed profile flags, and a content hash per installed file, computed from the fetched tree at install time. The receipt — written by an explicit, human-approved run — is the trust root for later updates; fork detection is a local hash comparison and needs no network.
- **Threat model (stated):** this covers accidental drift, stale copies, and transport corruption. A compromised upstream account or force-moved tag is out of scope — the same trust extended to any git dependency — with signed-tag verification noted as future hardening. A moved tag is *detected* (re-resolution no longer matches the receipt's commit) and stops the run. The receipt itself is editable state: a hand-edited receipt defeats fork detection, which stays inside the accidental-drift scope — the receipt attests, it does not prove.

**Install.** After writing the managed blocks, `llp-adopt` offers to install skills into the consuming repo's runtime skill directory. The install unit is a profile — **core** (default: the five existing skills, unchanged from LLP 0008; `llp-adopt` installs itself, and its update mode keeps the installation current) plus two **additive opt-in flags**: **review-plus** (`llp-super-refine`) and **delivery** (`llp-ship`, which also asks one question — this repo's default delivery mode, `local`, `pr`, or `direct` (§3) — recorded in a committed repo-local policy file, e.g. `.llp/policy.json`, never in a user-global receipt). Profile membership is defined by this RFC and, per release, by the tag's adopt contract. Installation is a copy, never a symlink. Existing security rules apply: confirm before writing, project-local may proceed more freely than user/global directories, reruns are idempotent, a file whose hash doesn't match the receipt is never overwritten without showing a diff, and user-global installs warn that they affect every repo for that user and require explicit confirmation.

**Update (a mode of `llp-adopt`).** Invoked as `/llp-adopt update` — and "update the LLP skills" routes here. An earlier revision made this a separate `llp-update-skills` skill; review showed the separation argument didn't hold: adopt already performs verified, diff-shown, receipt-writing update work in its bootstrap and migration paths, and a separate skill would duplicate that surface while growing the always-loaded core (LLP 0008, "Modes instead of more skills"). The posture boundary that matters — llp-maintain *never applies*, adopt applies after an approved diff — is preserved: llp-maintain's audit keeps its stale-pin note and hands off here.

1. Read the receipt for this installation (none → offer a fresh install, which bootstraps one; pre-receipt consumers migrate the same way). Runs are **single-flight** per installation: an unfinished update journal or unreconciled run state blocks a new run until recovered.
2. Resolve upstream: list release tags, resolve the chosen (default: newest) tag to its commit, fetch that tree *(advisory: shallow clone or tag archive; git is a prerequisite for install/update)*.
3. **Three-way check** per file: installed copy vs. receipt hash. Any mismatch means the project forked a managed file — the coupled update **aborts** (skills reference each other; mixed-release installs are not a supported state). The run reports the fork and offers resolution paths; it never clobbers, and it reruns only after resolution. Resolution is binary per file: discard the fork (restoring a managed copy), or **detach** it — the file leaves the managed set permanently, the receipt records the detachment, and the remaining managed files stay a complete coupled set for the profile *minus its detached members*, which later updates treat as user-owned (upstream changes to a detached file are noted, never applied). Detachment is not a supported-mixed release; it is a smaller managed set beside user-owned files.
4. Compute the changeset for the installed profile *as defined at the target tag* (adds, removals, renames included), present the full diff as one set, and on approval apply it. **Contract:** the state approved is revalidated immediately before mutation (a file edited between approval and apply aborts); an interrupted update is recoverable to either endpoint; the receipt write is the commit point; prior bytes remain retrievable until the update completes. *(Advisory mechanics: stage outside the target, journal the run, back up prior bytes, move, write receipt last; rollback after completion is `git revert` where the installation is committed, the backups otherwise.)*
5. If upstream is unreachable, a tag has moved or vanished, or fetched content can't be verified against the resolved commit: report exactly that and **write nothing**. Cannot-verify never degrades to guess.

**Alternatives.** Symlinks: rejected in LLP 0008. Plugin marketplace: single-runtime; possible later adapter. Submodules/subtrees: a second repo inside every consumer for a handful of markdown files. A per-release hash manifest file: dropped in review — the tag's tree already content-addresses the release, and a manifest inside the tag it attests adds consistency, not authenticity; it returns only if per-file raw fetch (no git) becomes a supported channel. A deterministic sync CLI: would make staging/atomicity mechanical but re-opens LLP 0008's no-CLI decision; revisit narrowly if the transaction outcomes above prove error-prone to achieve with shell primitives.

### 2. `llp-super-refine`

A new skill, invoked by a document's author, that runs a formal dual-family refine loop until convergence. It stays a separate skill rather than an `llp-review` mode on a posture line: `llp-review` gathers advice and **never applies anything**; super-refine is an orchestrating loop that *revises the document* between rounds and applies one pre-authorized status transition. Same reasoning that keeps apply-mode work out of llp-maintain. `llp-review` remains the right tool for advisory review at any intensity.

**Authorization.** Invocation is the LLP 0005 opt-in, recorded **per target, per author**: it names the target set, the reviewer families and runtimes, the redaction policy, and the round budget — that disclosure is what consent covers. Two authorities are distinct and both required: the *document author* authorizes the review and revision of the document; a *human with disclosure authority over the repository* (often, but not necessarily, the same person) authorizes the external sends — an AI co-author listed in metadata is never a disclosure authority, and the capsule's outbound inventory is disclosed before launch. Invocation authorizes (a) setting each named `Draft` target to `Review` at loop start (the document is factually under formal review from that moment), and (b) every external-model send within the disclosed budget. Redaction applies to surrounding context only, never to target bytes — a target that cannot be disclosed whole stops the loop rather than producing a verdict on bytes no reviewer saw. Already-`Review` targets proceed unchanged; `Accepted`/`Active`/`Superseded`/`Tombstoned` targets are **refused** — material post-acceptance change is the addendum/superseding-LLP path (LLP 0005). Expanding targets, providers, or budget requires renewed authorization. Authorization is the author's own invocation or a durably recorded authorization from the author; an unsupported assertion of relayed authority is not accepted. Convergence produces a **recommendation** — never `Accepted` or beyond. Because skills are adapters, not policy homes (LLP 0009), the rule lands as this sentence added to LLP 0005, with the Phase 2 implementation: *"An author's explicit invocation of a formal review loop constitutes the `Review` opt-in and authorizes the loop's revisions within its disclosed budget; the loop's external-model sends require authorization from a human with repository-disclosure authority — supplied by the same invocation when the invoker holds both capacities."* `llp-review`'s contract is untouched.

**Invocation options (sensible defaults, overridable).** *Stopping:* default is converge-until-ready within the round budget; `--rounds N` instead runs exactly N rounds and stops, reporting each family's verdicts and any open concerns — useful when the author wants "a couple of rounds of scrutiny," not a convergence guarantee (status handling is identical; convergence recommendations only apply if convergence actually occurred). *Reviser:* default is the orchestrating session — one editorial voice, and reviser ≠ reviewer holds trivially. `--reviser <family|model>` delegates revision to a fresh session of that model; `--reviser each` has each family's own editor session apply that family's feedback, in a stated order, composing one revision for the next round. In every mode the invariant is the same: **no session reviews a revision it edited**, and the artifact records who revised. *Reviewers:* per the round protocol below, exact models/runners/efforts per family may be specified; defaults are the strongest available per family.

**Round protocol.** Each round is an auditable unit:

- **Before launching reviewers**, persist the round record (run journal plus each target's artifact round header): round number, target content hashes, topology, reviewer runtimes, and the hash of the **review capsule** — a read-only export of the tree at the recorded revision with the targets' review artifacts, run journal, and orchestrator notes **structurally excluded**. Both reviewers receive the same capsule and the same instruction set (hashed into the record). Where a runtime cannot exclude structurally, instruction-based blindness is permitted but MUST be disclosed as such in provenance — it is self-attested, not proof, exactly as LLP 0005 says of provenance headers. If a target changes mid-round, the round is void.
- One review per family per round, from **fresh, mutually blind sessions**: one from the strongest available Claude-family model, one from the strongest available external family. The invocation (or the repo policy file) MAY specify the exact model, runner, and effort per family; provenance records what actually ran, and if a specified reviewer is unavailable the loop stops — never silently substitutes.
- **Each review is written to its family artifact immediately on receipt** — sealed from the other reviewer until both have landed, but never held only in memory (LLP 0005: reviews that happen leave artifacts). Failed, partial, or malformed responses are recorded as such and never count as reviews.
- Each review ends with an explicit verdict line. **`READY` means:** no unresolved MATERIAL concern about correctness, coherence, feasibility, safety, or decision quality. **Altitude rule:** a concern whose resolution would only add specification detail — without identifying a defective decision — is not MATERIAL at RFC altitude; the orchestrator dispositions it, in the artifact, to implementation-phase material rather than absorbing it into the document. Verdicts bind to the **capsule hash** — the reviewer-visible bytes — which, because target bytes are never redacted, also binds them to the exact target hashes; a verdict never claims coverage of anything outside its capsule. In multi-target runs the final round requires each family's per-target verdicts plus a set-level consistency verdict, all bound to the same capsule.
- Artifacts follow LLP 0005: one file per family per target, dated round sections, full provenance (family, exact runtime, effort, date, redaction status, method, revision hash), verbatim bodies with orchestrator notes outside them. In lockstep mode the cluster review is preserved verbatim exactly once (primary target's artifact); reviewers write per-target sections and verdicts; sibling artifacts carry the round record, their verdict, and a cross-reference.
- The orchestrating session revises and therefore never reviews.

**Bounds and escalation.** The loop runs within the authorized round budget — default three rounds per document — and a **launch ledger** records every reviewer launch; void, failed, and malformed launches don't count toward convergence but do count against a hard launch cap (default 2× the round budget per family per target). Cross-consistency re-reviews charge the affected document's budget. **Growth budget:** review-driven revisions may not grow a document net beyond ~20% over the revision that entered the loop; past that, additions must displace — length is spent deliberately, not accreted. Four terminal outcomes short of convergence, all escalating to the author with the open concerns and every altitude-rule disposition made across the run: budget/cap exhaustion; a cross-family contradiction on a material point (never adjudicated by orchestrator fiat); **sustained asymmetric disagreement** — one family READY on two consecutive revisions while the other family is NOT READY on both; and growth-budget exhaustion with MATERIAL concerns still open. Each escalation proposes a status disposition — stay `Review` pending author action, or revert to `Draft` — that the author applies. Feedback amounting to a fundamentally different design or a new LLP stops the loop for author authorization.

**Multi-document coordination.** `/llp-super-refine 0012 0013 0014` accepts multiple targets. The orchestrator inspects coupling (`Related:` headers, cross-references, shared `Systems:`, whether the docs express one design) and chooses a topology per cluster, stating the choice and rationale before starting: **independent loops** for loosely coupled targets (one sub-orchestrator each, revising only its own document), **lockstep rounds** for tightly coupled ones (reviewers receive the whole cluster and judge cross-document coherence; the orchestrator revises the set coherently between rounds). A **context preflight** bounds cluster size: a cluster that exceeds what a reviewer can hold with attention to spare is split into independent loops plus a stronger final consistency pass — the artifacts then say the set-level verdict is per-loop plus consistency-pass, never claiming a whole-set review no reviewer performed. Either topology ends with a **cross-consistency pass**: if any document changed after a sibling that references it converged, the sibling gets one more round, propagating until the full hash vector passes a round with no changes — subject to the budgets above. Convergence for the invocation means both families' final verdicts cover that exact final hash vector.

**Current instantiation (non-normative, dated 2026-07-22).** Claude Fable 5 at max effort; OpenAI `gpt-5.6-sol` at ultra effort via non-interactive Codex CLI. The skill contract names families only; this dated subsection is exempt from any post-acceptance design freeze and is updated as the frontier moves (or superseded by the deferred `llp.json`, LLP 0008 OQ2).

*Note:* this RFC's own refinement ran under the `exact` prototype of this skill (invocation-authorized, `.fable`/`.codex` artifact naming, instruction-based blindness disclosed in its artifacts, status change at convergence rather than loop start). It predates the protocol above and is not a conforming acceptance test; Phase 2 includes one.

### 3. `llp-ship`

**Trigger and preflight.** A human hands over task references — Linear tickets, filesystem tickets, LLP documents, or free text — via `/llp-ship <ref...> [--base <branch>] [--mode local|pr|direct]`. Preflight discovers and states, before any mutation: the git repo and base branch (git is **required**; in a non-git project the skill refuses and offers plain task execution outside this contract); the recorded base SHA and its upstream relationship (pre-existing unpushed commits are surfaced and never made remotely reachable by this run without explicit consent); the verification commands available (the project's tests; `ref-check` where present — optional per LLP 0001, absence stated, not papered over); reviewer availability, when the review intensity in effect requires one (no reviewer at `same-family`+ → `blocked`; at `none`, none is needed); and the delivery mode and review intensity. **Authority:** the policy file's recorded mode is a *default and ceiling*, read from the recorded base commit — it is not itself authorization. External writes (`pr`, `direct`) are authorized by the human invocation that requested them, with the mode stated at preflight; task *content* never grants or escalates authority. Runs are single-flight per repo (an unreconciled run ledger blocks a new run until recovered). Any missing mandatory capability stops the run as `blocked`, honestly.

**Task gating.** A proposal-shaped LLP task — one whose design others will implement, regardless of its `Type:` — must be `Accepted` before a delivering run implements it (LLP 0005). If it isn't, ship stops: the author can accept it (their action, not ship's) and re-invoke, or direct an explicitly-labeled **experiment run**, which implements on run branches and delivers nothing. Ship never applies *author-authority* transitions (`Accepted`, tombstoning). `Accepted` → `Active` is different — LLP 0005 defines it as the factual completion transition, and it is **not author-restricted**: anyone completing and delivering the implementation may apply it. When a delivered candidate completely implements an `Accepted` document, the flip is included in the gated candidate as a clearly-called-out commit, named in the run report/PR body so the delivering human is knowingly endorsing it. A partial implementation states its partial state and flips nothing. (LLP 0005 gains a clarifying clause to this effect with Phase 3.)

**Plan phase.** Read every task fully (each task's source and content hash snapshotted in the run ledger); orient via governing docs; restate free-text tasks as a concrete plan before executing. Build the dependency graph and choose lanes *(advisory: independent tasks parallel in separate worktrees; dependent tasks sequenced in one lane)*. If lanes will create LLP documents, reserve their numbers serially at plan time — no `max + 1` race at merge within this invocation (cross-invocation collisions remain LLP 0009 OQ1's general problem). Before creating anything, write the **run ledger** (durable, local, prunable after reconciliation; e.g. `.llp/ship-runs/<run-id>.json`): run id, base SHA, mode, task snapshots, and every branch/worktree the run creates — written before creation, updated at each gate. Git refs remain the source of truth; the ledger records intent and evidence, and a later invocation reconciles it against git to find and offer to reclaim orphans.

**Execute, integrate, gate.** The base branch is immutable during execution — every run, including single-task runs, works on run-namespaced branches (`llp-ship/<run-id>/…`) and integrates on a run-specific integration branch cut from the recorded base SHA. Per lane: implement with commits at natural boundaries, co-evolving docs and `@ref`s (LLP 0004); run lane-local verification for fast feedback. Then the gates, indexed by commit SHA:

- **CANDIDATE(SHA):** all lanes merged into the integration branch, conflicts resolved.
- **VERIFIED(SHA):** the stated verification suite passes on a clean checkout of exactly this SHA (a run that mutates tracked files fails the gate — the mutation belongs in a commit).
- **REVIEWED(SHA):** review intensity is **tunable policy, not invariant** (capability-graded per LLP 0004 — the right default falls as models improve): repo policy or invocation selects `none` | `same-family` (default) | `cross-family` (§2's primitive). When any review runs: a fresh, independent session that wrote none of the code reviews the integrated diff and issues an **explicit verdict that no material finding remains** for this SHA — a review having occurred is not the gate; the verdict is. The reviewer never implements its own findings: material findings go to an implementing session, producing a new SHA that re-enters at CANDIDATE. Findings, dispositions, verdict, and the intensity in effect are recorded in the run report; at `none`, the report states plainly that delivery was unreviewed. What stays invariant at every intensity is honesty: claimed review must be real, SHA-bound, and independent.
- **DELIVERED:** only a SHA currently holding VERIFIED (and REVIEWED, at any intensity above `none`) may deliver, and delivery re-resolves local and remote base refs first — if either moved from the recorded SHA, reintegrate and re-gate or end `blocked`. Base advances only by fast-forward with an expected-old-SHA check; the outbound commit closure is computed before any push, and every commit that would become remotely reachable must be run-owned or explicitly authorized.

**Delivery modes.** With no recorded policy **the default is `direct`** — shipping means shipping: the human invoking ship is choosing to push, and that invocation is the authorization (author decision, 2026-07-23). Repos that want a PR gate record `pr` (or `local`) in policy — the delivery-flag install asks exactly this question, so consuming repos set their own default at install time and the naked default chiefly governs the solo-maintainer case. **`local`**: fast-forward the local base; push nothing. **`pr`**: push the integration branch and open a pull request; base untouched. **`direct`**: advance and push the base; before pushing, state exactly which commits will publish; a rejected push (branch protection, divergence) falls back to `pr` behavior, reported factually. Ship's external effects are limited to git delivery (pushes, PR creation) — a task implying other external effects (deploys, package publishes, tracker writes) is out of ship's scope, and that portion is reported as out-of-scope rather than silently attempted. External steps can partially succeed; the ledger records **each external effect as its own fact** (e.g. `branch-pushed`, `pr-opened`, `remote-base-advanced`), the run reconciles those facts against the remote before any retry, and a task's terminal status always enumerates them — a task may end `blocked` on a remaining step (say, PR creation), but a report MUST NOT conceal or contradict an effect that succeeded (the branch *is* pushed, and the report says so). PR creation is a capability-checked attempt; work is preserved, never force-pushed. Multi-task delivery is atomic by default: one gated SHA delivers everything; delivering a reduced subset requires renewed human approval and full re-gating. The run report (task outcomes, verification output, review verdict and dispositions, delivered SHA) goes in the PR body in `pr` mode and is retained in the run ledger in `local`/`direct` modes.

**Invariants** (the pinned MUSTs of the eventual contract):

- MUST NOT report verification or review that did not run; failed checks are reported as failures. Both gates MUST hold for the exact SHA delivered.
- MUST NOT count a self-review as the review: at any intensity above `none`, the reviewer is distinct from every implementing session and never implements its own findings; at `none`, the report MUST say the delivery was unreviewed.
- MUST NOT force-push, and MUST NOT make any commit remotely reachable that the run did not create, absent explicit consent.
- MUST record every created branch/worktree in the run ledger before creating it, namespace them `llp-ship/<run-id>/`, and clean up only state that is clean and durably integrated. MUST NOT delete a dirty worktree or a branch holding unique unmerged commits — on failure or abort, preserve them and report exact recovery instructions.
- MUST leave unrelated local changes and commits untouched; uncommitted user changes that block the plan → stop and ask, never stash silently.
- MUST report per task: done (with commits), blocked (on what), or failed (with actual output) — and after any external effect, the factual outcome of that effect.

## Consequences

- LLP 0008's five skills become seven, organized as core plus additive flags; its skills table, hand-offs, and the `AGENTS.md`/README skill index gain adopt's install/update mode, `super-refine = dual-model refine-until-ready`, and `ship = tasks done end to end`. LLP 0005 gains the quoted authorization sentence (§2). LLP 0001 (the adoption guide) gains the install step. **LLP 0009 is revised in the same phase**: this RFC supersedes its classification of distribution machinery as absent shell — receipts and the update transaction become first-party — while its capability test, the ≤60-line contract cap, and the five-skill *core* stand. Each of these lands **with the phase that implements it** — there is no standalone documentation phase (LLP 0004 co-evolution). The `.llp/policy.json` file is a partial instantiation of LLP 0008 OQ2's deferred `llp.json`; consolidating them later revises that answer, not a new surface.
- Two new skill directories, `skills/llp-super-refine/` and `skills/llp-ship/`, each a ≤60-line contract (Trigger · Invariants · Artifact · Hand-offs) citing this RFC and LLP 0005/0008 as pinned upstream URLs; `skills/llp-adopt/` grows its install step and update mode. **Contract-first rule:** each phase begins by drafting its contract; if a contract cannot carry its invariants within the line cap, that is a blocking finding brought back to the author, not a rule silently dropped.
- Release discipline on this repo, with a checklist in the adopt contract's recipe: bump `source:` pins and pinned URLs → commit → tag → push tag. Release validation, if ever automated, is a separate composable check — `ref-check` keeps its single purpose and size (LLP 0009).
- The `exact` project's `llp-super-refine` becomes a consumer of the first-party skill (a pinned copy with a receipt) instead of the origin.

## Implementation plan

Independently landable phases, risk-ordered; each starts with its contract draft and lands its own doc reconciliation (above):

1. **Receipts + install + update mode** (`llp-adopt`, LLP 0001/0008 updates, release checklist). Acceptance: clean-room install from a tag; idempotent rerun; a hand-edited skill aborts the coupled update with resolution paths; migration of a pre-receipt consumer (use `exact`); an interrupted update recovers to either endpoint; edit-between-approval-and-apply aborts; concurrent second run blocked; offline and moved-tag runs end "cannot verify, wrote nothing."
2. **`llp-super-refine`** (+ the LLP 0005 sentence, landing together). Acceptance: a conforming single-doc run with capsule-hashed, verdict-lined artifacts and the round record persisted pre-launch; a crash after one review leaves that review's artifact intact; forced non-convergence hits the budget and escalates; a sustained-asymmetry run stops after two consecutive one-sided READYs; a two-doc lockstep run yields per-target plus set-level verdicts on the final hash vector; refusal of an `Accepted` target.
3. **`llp-ship`** (riskiest, last). Acceptance: two-lane run delivering via `pr` with the report in the PR body; lane-passes/integration-fails caught at VERIFIED; a review finding produces a new SHA that re-enters gating; base moved mid-run triggers reintegration or `blocked`; a push-succeeds/PR-fails run reports `branch-pushed` alongside the blocked step; abort preserves ledger, recovery instructions, and unique commits; a non-`Accepted` proposal-shaped task stops at gating; a completed implementation includes a clearly-called-out `Accepted` → `Active` commit in the gated candidate; a run at intensity `none` delivers with "unreviewed" stated in its report.

## Open questions

1. **Skill-count pressure.** Core stays five, but flagged consumers load up to seven descriptions (LLP 0008's token-footprint question). Consolidation candidates should come from observed low usage once consumers exist — no skill is pre-exempt.
2. **Degraded super-refine.** When the external family is unavailable, the loop stops. Worth adding a *deferred-second-family* mode — single-family rounds to a provisional verdict, the document marked as owing one cross-family round before `Accepted` may be proposed? It preserves the guarantee's meaning while tolerating outages.
3. **Namespace.** `llp-ship` is general task execution, only incidentally LLP-flavored. It keeps the `llp-` prefix for family cohesion; a future split — generic shipping engine, thin LLP adapter — is plausible if non-LLP repos want it.
4. **Round-budget and growth-budget defaults.** Three rounds and ~20% are guesses from `exact` experience; the round records' telemetry should tune both, and could justify per-stakes defaults.
5. **Evidence obligation.** What usage data (invocation counts, convergence rates, asymmetric-stop frequency, prevented failures, token cost) should the first consuming repos collect so LLP 0009 Phase 4's proof obligation — and OQ1 here — can be answered with observations rather than predictions? Install receipts (origin, tag, date) are a natural longitudinal dataset.
